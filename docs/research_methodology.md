# Research methodology

**Dissertation:** *Development of an Intelligent User Review Analysis System Using Natural Language Processing and Machine Learning Methods*

This document describes how the system's datasets, models and evaluations are produced. Measured results are kept separately in [`experiment_results.md`](experiment_results.md). Every number there is copied from a machine-generated report under `reports/`.

---

## 1. Research problem and objectives

User reviews are abundant, unstructured and noisy. Manufacturers and buyers need (a) a reliable estimate of a review's overall sentiment and (b) evidence about *which product aspects* drive dissatisfaction, without reading thousands of reviews.

**Objectives**

| # | Objective | Where it is implemented |
|---|---|---|
| O1 | Build a reproducible pipeline from raw review data to labelled train/validation/test splits | `src/review_intel/data/`, `scripts/prepare_data.py` |
| O2 | Train and compare classical (TF-IDF + linear) and transformer (DistilBERT) sentiment classifiers on the same splits | `src/review_intel/models/`, `scripts/train_*.py` |
| O3 | Evaluate them with metrics suited to imbalanced 3-class data and select one model without touching the test set | `src/review_intel/evaluation/`, `scripts/evaluate_models.py` |
| O4 | Provide aspect-level and product-level analytics that report evidence (counts, excerpts) | `src/review_intel/analytics/` |
| O5 | Expose the models and analytics to AI applications through a standard integration layer (MCP) | `review-analyzer-mcp/server.py` |

**Research questions**

- RQ1: How do TF-IDF + Logistic Regression, TF-IDF + Linear SVM and fine-tuned DistilBERT compare on 3-class review sentiment in terms of macro-F1, per-class F1 (especially the minority *neutral* class) and inference cost?
- RQ2: Is the extra cost of a transformer justified by the size of its improvement, given the latency and hardware requirements?
- RQ3: Can a transparent lexicon-plus-classifier approach surface plausible aspect-level problems, and what are its limits?

## 2. Dataset source and access

**Amazon Reviews 2023**, McAuley Lab, UC San Diego. Hou, Y., Li, J., He, Z., Yan, A., Chen, X., McAuley, J. *Bridging Language and Items for Retrieval and Recommendation*. arXiv:2403.03952, 2024. https://amazon-reviews-2023.github.io/

- **Category:** Electronics. The official page reports 43.9M ratings, 18.3M users and 1.6M items. Our streaming pass counted **43,886,944 review lines** (`data/raw/amazon_electronics/download_manifest.json`).
- **Access:** the official direct file `review_categories/Electronics.jsonl.gz` (≈6.5 GB compressed, ≈22.6 GB uncompressed) and `meta_categories/meta_Electronics.jsonl.gz`. They were downloaded over HTTPS from `mcauleylab.ucsd.edu` by `scripts/download_amazon.py`. The Hugging Face mirror (`McAuley-Lab/Amazon-Reviews-2023`) exposes the same files; its `benchmark/` CSVs contain IDs and ratings only (no review text), so they are not usable for sentiment.
- **Licensing and terms:** the dataset web page does not state an explicit licence. The data is released by the authors for research. We (1) cite the paper, (2) use it for non-commercial academic research only, (3) do not redistribute raw reviews: `data/raw/` and `data/processed/` are git-ignored and only manifests are committed, and (4) drop the reviewer ID (`user_id`) from processed files. **Action for the author:** confirm the terms with your supervisor or the dataset maintainers before publishing any derived data.
- **Synthetic data is never research data.** `review-analyzer-mcp/reviews.json` (5 reviews) and `data/fixtures/synthetic_reviews.csv` (73 rows, generated by `scripts/make_fixture.py`) are synthetic. They exist for tests and demos and their manifests carry `"is_synthetic": true`. No result on them is reported as a research result.

### 2.1 Sampling

The review file is ordered by **user**, not randomly, so its first *N* lines would cover only a few thousand reviewers. We therefore stream the entire file once, without storing it, and draw a **uniform random sample** with reservoir sampling (Algorithm R, seed 42). Every review has the same probability of selection, 100,000 / 43,886,944 ≈ 0.23%. The SHA-256 of the resulting sample file is `6f4a0a50e67b31baed23b321218d6b403cbbc5b7cbdbe326a57a406166c0fc55`.

**Analytics corpus (descriptive tools only).** The script also implements a second pass, which collects up to 1,000 reviews (per-product reservoir) for each of the 10 most-reviewed products, excluding research-sample reviews, and a third pass for product titles. *In this project those passes did not complete:* the source server first closed the connection mid-stream, and after the resume bug was fixed the rerun was throttled to about 0.07 MB/s. As a result, the pass-1 product counts and the download manifest were not persisted for the original run. The script now writes them after each pass. The analytics corpus actually used is therefore the **held-out test split** (9,659 reviews; never used for training or selection), with titles for its 25 most-reviewed products read column-wise from the official metadata Parquet files on Hugging Face (`scripts/fetch_product_titles.py`). It is used only for descriptive analytics after the single test evaluation, so it does not affect any reported metric.

### 2.2 Per-product analytics corpus (collected 2026-10-15)

The original analytics corpus supports almost no product-level conclusions: only 1 of its 8,177 products has 30 or more reviews. A separate **per-product corpus** was therefore collected. It is used only by the MCP analytics tools. It was not used for training, tuning or evaluation, so no reported metric changes.

- **Source and access.** The UCSD server was still throttled (0.08 MB/s measured on 2026-10-15). The same review file is published uncompressed on the official Hugging Face mirror `McAuley-Lab/Amazon-Reviews-2023` (`raw/review_categories/Electronics.jsonl`, 22,616,233,652 bytes). The run read it pinned to commit `2b6d039ed471f2ba5fd2acb718bf33b0a7e5598e`. No credentials are needed, and the dataset is not gated. Two checks show the mirror is the same file: the first 2,000 lines are byte-identical to the UCSD file, and the full read counted 43,886,944 review lines, exactly the count of the original sampling pass.
- **Licence.** Neither the dataset website nor the Hugging Face card states a licence. The data is used for non-commercial research with the citation (Hou et al., 2024). Raw files stay local (`data/raw/` is git-ignored) and are not redistributed.
- **Product selection.** The 50 products with the most reviews in the uniform research sample. A product's count in a uniform sample is an unbiased estimate of its share of the category, so no separate counting pass over 43.9M reviews was needed.
- **Sampling within a product.** Up to 1,000 reviews per product, chosen by *bottom-k* sampling: each review gets the priority `sha1(seed | review_key)` (seed 42), and the 1,000 smallest per product are kept. This is a uniform random sample without replacement. It depends only on the reviews themselves, so it is identical however the file is chunked, parallelised or resumed (tested).
- **Review key and duplicates.** The dataset has no review id. A review is identified by `user_id|parent_asin|asin|timestamp`, and copies with the same key are dropped. Each review's byte offset in the source file is kept as a stable id (`source_offset`).
- **Exclusions.** Every review whose key is in the research sample (train, validation and test) is excluded. The analytics corpus therefore contains no review the models were trained, tuned or tested on. Identical *texts* written by other customers are possible and are counted in the validation report.
- **Resumability.** The file is read in 85 byte-range chunks of 256 MB by 4 threads. Each finished chunk is saved, so an interrupted run resumes with the same command. Parameters are checked against the saved plan, and a resume with different parameters is refused.
- **Titles.** Product titles come from the official metadata (`raw_meta_Electronics` Parquet files on the same mirror), read column-wise. Products without a title stay unnamed.
- **Text de-duplication** is *off* for this corpus (`deduplicate: false`). Duplicates were already removed by key, and the pipeline's text de-duplication works across products, so it would wrongly merge, for example, two customers' "Works great" reviews of different products.

## 3. Inclusion and exclusion criteria

Applied in `review_intel.data.pipeline.clean_records`. Every exclusion is counted in the dataset manifest.

| Criterion | Rule |
|---|---|
| Text | Title and body are joined as `"<title>. <body>"`. Text is excluded if it has fewer than 3 non-space characters after cleaning. |
| Auto-generated titles | Titles of the form "One Star" … "Five Stars" are **removed** before joining. Amazon generated them from the rating, so they would leak the label into the input. |
| Rating | Must be a whole number from 1 to 5. Missing, non-numeric, out-of-range and fractional values are excluded, not rounded. |
| Product | A product identifier (`parent_asin`) must be present. |
| Exact duplicates | Texts equal after case-folding and whitespace normalization: the first copy is kept if all copies share a label. **All** copies are dropped if their labels conflict, because the text is then ambiguous. Deduplication happens *before* splitting. |

## 4. Label construction

Ratings are mapped to three classes with a fixed, documented rule (`review_intel.data.labels`):

| Stars | Label |
|---|---|
| 1-2 | negative |
| 3 | neutral |
| 4-5 | positive |

Star ratings are a **proxy** for sentiment, not human sentiment annotations (see Threats to validity). A dataset can instead supply an explicit label column (`label_source: "column"`).

## 5. Preprocessing

**Stateless steps**, applied identically to all splits and learning nothing from data: Unicode NFKC normalization, HTML entity unescaping and tag removal (`<br />`), URL replacement, whitespace collapsing. Case is kept: the TF-IDF vectorizers lowercase internally, and the DistilBERT tokenizer is uncased.

**Learned steps**, fitted on the **training split only**: the TF-IDF vocabulary and IDF weights live inside each scikit-learn `Pipeline`. The DistilBERT tokenizer is the pretrained one, and fine-tuning uses only training data. Stop words are not removed for classification, since negations such as "not" carry sentiment. Lemmatization is not used, because it brings no clear benefit to TF-IDF models with n-grams.

## 6. Experimental design

### 6.1 Splits

A stratified random split into **80% train / 10% validation / 10% test** with seed 42 (`split.strategy = "stratified"`). This preserves the class distribution in each split. A grouped split (`"group"`, e.g. by reviewer or product) is implemented and tested for leakage-sensitive experiments.

### 6.2 Models

| Model | Implementation | Tuned on validation |
|---|---|---|
| **A** TF-IDF + Logistic Regression | word 1-2-grams (min_df 2, max_df 0.95, ≤200k features, sublinear tf), optionally plus character 3-5-grams (`char_wb`, ≤300k); `LogisticRegression(lbfgs)` | feature set ∈ {word, word+char}; C ∈ {1, 4, 16}; class_weight ∈ {balanced, none} |
| **B** TF-IDF + Linear SVM | same feature sets; `LinearSVC` | C ∈ {0.05, 0.2, 0.5}; class_weight ∈ {balanced, none} |
| **C** DistilBERT | `distilbert/distilbert-base-uncased` + classification head, fine-tuned end to end; AdamW (lr 5e-5, wd 0.01), linear warmup (6%) and decay, class-weighted cross-entropy, max length 256, batch 32, bf16 autocast on GPU | best epoch by validation macro-F1 (2 epochs) |
| Reference | keyword-count baseline from v1 | none; not a trained model, kept for transparency only |

The grids are in `configs/models/baselines.json` and `configs/models/distilbert.json`.

**Grid revision (validation only).** The first grid (LogReg C ∈ {1, 4, 16}; SVM C ∈ {0.05, 0.2, 0.5}) put the best C at the lower edge for both families, so it was extended downward (LogReg {0.25, 0.5, 1, 4}; SVM {0.01, 0.02, 0.05, 0.2}). Both optima then lay inside the grid (LogReg C=0.5, SVM C=0.05, both word+char features with balanced class weights). This decision used validation macro-F1 only and is recorded in `configs/models/baselines.json` (`_grid_history`).

**Precision note.** During training, DistilBERT's per-epoch validation macro-F1 is computed under bf16 autocast (epoch 2: 0.7441). The reported validation figure (0.7444) comes from re-evaluating the saved artifact in fp32 exactly as it is served. The 0.0003 difference is numerical.

### 6.3 Model selection

1. **Within a family:** the configuration (or epoch) with the highest **validation macro-F1**.
2. **Across families:** the highest validation macro-F1. Ties at 4 decimals are broken by the fixed order LogReg → SVM → DistilBERT (cheaper model first). The rule is deterministic, unlike a latency tie-break, which depends on timing noise.
3. The selection is written to `reports/<dataset>/model_selection.json`. Only then does `scripts/evaluate_models.py test` read the **test split**, and it refuses to run without a recorded selection. The non-selected models may also be evaluated on test for the comparison table; they are labelled *post-selection* and played no part in any decision.

The final models are trained on the training split only; they are not refit on train+validation before testing. That way the reported test score belongs to exactly the artifact that is deployed.

## 7. Evaluation metrics and justification

| Metric | Why |
|---|---|
| **Macro-F1** (primary) | The classes are heavily imbalanced (≈75% positive). Accuracy would reward predicting "positive" for everything. Macro-F1 weights each class equally, so performance on the rare *neutral* class counts. |
| Accuracy | Familiar headline number; reported for completeness. |
| Macro precision / recall | Separates over-prediction from under-prediction across classes. |
| Per-class precision / recall / F1 + confusion matrix | Shows which classes are confused; neutral ↔ positive/negative is the expected hard case. |
| ECE, top-label expected calibration error, 15 bins (probabilistic models only) | Checks whether "probabilities" can be read as confidence. LinearSVC outputs uncalibrated decision scores and is labelled as such, never as probabilities. |
| Training time | Wall-clock time to fit the selected configuration: vectorizer plus classifier, or all fine-tuning epochs. |
| Inference latency | See the method below. |

**Latency method** (`review_intel.evaluation.metrics.measure_latency`): 300 texts are sampled with a fixed seed from the evaluated split. After 20 warm-up calls, each text is predicted alone (batch size 1). We report the median and the 95th-percentile wall-clock time per call (`time.perf_counter`), including vectorization or tokenization. Throughput is measured by predicting the same texts in batches of 256 and reported in texts per second. Measurement is in-process on the hardware listed in each report, with no network or disk I/O. DistilBERT runs on the GPU if available; the device is recorded.

## 8. Data leakage prevention

- Deduplication runs **before** splitting, and every manifest checks that no text appears in two splits (`leakage_checks.text_overlap_* = 0`).
- Learned preprocessing (TF-IDF) is fitted inside the pipeline on training data only.
- Hyperparameters and epochs are chosen on validation data. The test split is read once, by a separate command, after the selection is recorded. A unit test (`test_training_never_reads_test_split`) checks that training code never loads `test`.
- Auto-generated star titles ("Five Stars") are removed, so the rating cannot leak through the text.
- The analytics corpus excludes every review that is in the research sample.
- **Remaining overlap (reported, not removed):** popular products appear in several splits (`product_overlap_*` in the manifest). The model can learn product-specific vocabulary. This is realistic for deployment on known products, but it is a threat to generalization to unseen products. A product-grouped split can quantify it.

## 9. Reproducibility

- Fixed seeds (42) for sampling, splitting, classifiers and fine-tuning (Python, NumPy and PyTorch RNGs, plus a seeded DataLoader generator).
- Every stage writes a JSON record: `download_manifest.json` (source URL, HTTP headers, line counts, seed), the processed `manifest.json` (config, SHA-256 of the input file, exclusion counts, class distributions, split sizes, leakage checks, package versions), model `metadata.json` (parameters, dataset reference, SHA-256 of the weights, package versions), and validation and test reports with environment information.
- The source file has no version identifier. The download manifest records its `Content-Length` and `Last-Modified` headers, so a changed upstream file can be detected.
- Known nondeterminism: GPU kernels (cuDNN/cuBLAS) are not forced to be deterministic, so DistilBERT results can differ slightly between runs and machines. Classical models are deterministic given the same package versions.

## 10. Aspect-based analysis (method and status)

Aspect analysis uses a transparent v1 method, **not** a trained ABSA model:

1. Reviews are split into sentences (punctuation rule).
2. An aspect is detected when a sentence contains a term from a configurable lexicon (`configs/aspects.json`: battery, camera, screen, performance, price, design, delivery, sound, connectivity, setup, remote, customer service), matched on word boundaries.
3. The selected sentiment model classifies each mentioning sentence.
4. Counts per aspect and sentiment are aggregated, and the highest-scoring sentences are returned as evidence.

Limitations: lexicon recall and precision were not measured. A sentence mentioning two aspects gives both the same label. The sentiment model was trained on whole reviews labelled by stars and is applied to sentences (a domain shift). Sentence-level accuracy has **not** been evaluated, because no sentence- or aspect-level gold labels exist in this dataset. The module is behind an interface (`AspectExtractor` plus a prediction function), so a learned extractor or ABSA model can replace it.

## 11. Limitations and threats to validity

- **Construct validity:** star ratings are a proxy for sentiment. A 3-star review can be clearly positive or negative in its text, and some 5-star texts are complaints. "Neutral" is the noisiest label.
- **Internal validity:** dropping conflicting duplicates removes short, ambiguous texts (e.g. "Works great" rated 3 and 4) from every split. This slightly simplifies the task. The counts are reported in the manifest.
- **External validity:** a single category (Electronics), English only, Amazon only. Results may not transfer to other domains, languages or platforms.
- **Sampling:** the sample is uniform over *reviews*, so heavy reviewers and popular products are represented proportionally to their review counts.
- **Statistical:** a single train/validation/test split with one seed. No confidence intervals or significance tests are computed yet; bootstrap CIs over the test set are a planned extension. Differences of a few thousandths in macro-F1 should not be over-interpreted.
- **Model capacity vs budget:** DistilBERT is trained for a fixed small number of epochs without a hyperparameter search. The classical models had a small grid, so the comparison is between *reasonably tuned* models, not exhaustively tuned ones.
- **Aspect analytics:** descriptive only; not validated against human aspect annotations.

## 12. The role of MCP

The **Model Context Protocol** (MCP) is an *integration layer*, not part of the NLP/ML research contribution. MCP is not a model and performs no sentiment analysis. It standardizes how an AI application (Claude Desktop, Claude Code, MCP Inspector, agent frameworks) discovers and calls tools:

- `review_intel` (the research system) contains the data pipeline, models, evaluation and analytics, and is fully usable without MCP.
- `review-analyzer-mcp/server.py` publishes those capabilities as typed, documented MCP tools such as `analyze_sentiment` and `get_product_summary`. It validates arguments and returns structured results with evidence.

This separation keeps the research results independent of the integration technology. The contribution of the MCP layer is engineering: it shows that the trained model and analytics can be used by LLM-based assistants in a safe, read-only and auditable way.
